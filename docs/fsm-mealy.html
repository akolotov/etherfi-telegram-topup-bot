FSM бота пополнения аккаунта: автомат Мили

Модель описывает один экземпляр автомата на одного сконфигурированного Telegram-пользователя. Глобальный диспетчер сначала проверяет JSON-конфигурацию: если пользователя там нет, start, сообщения и callback-события игнорируются и экземпляр FSM не создается.

Это расширенный автомат Мили: состояние определяет режим работы, а выходы выполняются на переходах. Счетчики, deadline cooldown, id последнего кнопочного low-balance сообщения и id Safe-транзакции являются persisted context и восстанавливаются после перезапуска бота. Последний прочитанный баланс не нужен для восстановления FSM и может храниться только как debug/observability поле.

Состояния

S0 NotStarted

Пользователь еще не сделал start или заблокировал бота. Таймеры остановлены, runtime-контекст очищен.

S1 Monitoring

Активная периодическая проверка баланса target account через balance check interval.

S2 LowPrompt

Отправлено последнее сообщение о низком балансе с валидными кнопками Top Up и Ignore.

S3 LowCooldown

Лимит low-balance нотификаций исчерпан. Проверка баланса продолжается, новые low-balance сообщения подавлены до cooldown.

S4 SafeTxPending

Safe-транзакция создана, пользователь уведомлен. Бот проверяет баланс и статус Safe-транзакции на каждом тике; напоминание о pending-транзакции отправляется без кнопок.

Сигналы

Группа Сигнал Смысл
Telegram START_CONFIGURED Сконфигурированный пользователь сделал start или визуальный restart после блокировки.
Telegram START_UNKNOWN, USER_MESSAGE, REPLY, REACTION События, которые бот не должен обрабатывать, кроме start от сконфигурированного пользователя в S0.

Telegram STALE_CALLBACK Нажатие на старые кнопки или callback в состоянии, где кнопки не ожидаются.
Telegram USER_BLOCKED, SEND_403 Пользователь заблокировал бота или Telegram вернул 403 при отправке сообщения пользователю.
Timer BALANCE_TICK Периодический тик через target account balance check interval.
Onchain BALANCE_OK, BALANCE_LOW, BALANCE_READ_FAILED Результат синхронной проверки баланса Optimism target account на тике или внутри CLICK_TOP_UP: low, ok или ошибка чтения.
Safe SAFE_TX_CREATE_OK, SAFE_TX_CREATE_FAILED Результат создания или регистрации транзакции в Safe Wallet сети Arbitrum.
Safe SAFE_TX_PENDING, SAFE_TX_FINAL, SAFE_TX_STATUS_READ_FAILED Статус созданной Safe-транзакции: pending, executed/cancelled либо ошибка чтения статуса.
Lifecycle BOT_RESTART Перезапуск процесса. FSM восстанавливает persisted state, таймеры и ближайший тик.

Определения guard

  • BALANCE_LOW: последний прочитанный баланс target account в Optimism строго меньше target account balance threshold.
  • BALANCE_OK: последний прочитанный баланс target account в Optimism больше либо равен target account balance threshold.
  • freshBalance: баланс target account в Optimism, синхронно прочитанный внутри перехода CLICK_TOP_UP(latest) непосредственно перед расчетом amount и созданием Safe-транзакции.
  • low balance notification limit считается количеством отправленных low-balance сообщений в текущем цикле, включая самое первое сообщение.
  • Все user-facing send actions имеют неявную ветку SEND_403: output action прерывается, таймеры пользователя и runtime-контекст очищаются, persisted state сохраняется как S0 NotStarted.
  • BOT_RESTART: загрузить persisted context, для всех state != S0 пересоздать periodic timer по nextTickAt; если nextTickAt <= now, выполнить тик сразу или запланировать его немедленно.
  • В S4 Safe status проверяется независимо от balance read; SAFE_TX_FINAL очищает pending-транзакцию даже если чтение баланса на этом тике завершилось ошибкой.
  • Если в S4 баланс прочитан как BALANCE_OK, FSM очищает pending-транзакцию по факту пополнения target account, даже если Safe status на этом тике недоступен.

Known limitations / future recovery

  • Если Safe-транзакция уже создана, но отправка пользователю tx-created notification завершается SEND_403, текущая FSM применяет общую ветку 403: очищает runtime-контекст и сохраняет S0 NotStarted. Это известное ограничение текущей модели.
  • На практике это может потерять знание о существующей pendingSafeTxId, хотя транзакция уже зарегистрирована в Safe Wallet.
  • Future recovery: перед созданием новой Safe-транзакции и/или на START_CONFIGURED делать reconcile через Safe Wallet API и проверять, нет ли уже pending transaction для данного target account/recipient.

Persisted context

Минимальный набор данных, который стоит хранить для восстановления после перезапуска:

  • state: одно из S0..S4.
  • notificationCount, lowCooldownUntil, txReminderUntil.
  • currentMessageId: только последняя low-balance нотификация с кнопками считается валидной; в S4 callbacks не ожидаются.
  • pendingSafeTxId и, при необходимости, Safe nonce/hash для проверки статуса.
  • lastBalanceCheckedAt, nextTickAt.
  • notificationSentAt или производные deadlines, если после restart нужно точно восстановить cooldown-окна.
  • Последний прочитанный баланс можно хранить только как optional/debug поле; восстановление FSM и расчет Safe tx amount от него не зависят.
  • Флаг started можно выводить из state != S0; после block/403 состояние и контекст очищаются.

Инварианты

  • Только S2 и S3 принимают callback от последнего low-balance сообщения с кнопками.
  • Любая отправка пользователю, завершившаяся 403, эквивалентна USER_BLOCKED; переход, во время которого случился 403, не считается успешно завершенным.
  • Если баланс стал больше либо равен threshold, low-balance счетчики и cooldown сбрасываются независимо от текущего active/pending режима.
  • Если создание Safe-транзакции не удалось, FSM уведомляет админа и возвращается к обычному мониторингу.
  • При существующем pendingSafeTxId пользовательские callbacks не ожидаются; нажатия на старые Top Up/Ignore считаются stale и игнорируются.
  • Amount Safe-транзакции всегда рассчитывается из freshBalance, прочитанного прямо в переходе CLICK_TOP_UP, а не из сохраненного последнего баланса.
  • После каждого BALANCE_TICK FSM сохраняет новое состояние после перехода и обновленный nextTickAt = tickHandledAt + target account balance check interval.
  • Safe-транзакция создается в Arbitrum из safe account; факт пополнения target account в Optimism определяется только последующими проверками баланса.
  • low balance notification limit должен быть не меньше 1; если он равен 1, первое low-balance сообщение сразу переводит FSM в cooldown.
